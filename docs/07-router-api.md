# Договор: управление обходом на роутере из Windows-приложения

Версия API 1, 2026-10-16. Сторона роутера — пакет `dpishell` (`06-router-spec.md`), сторона ПК — DpiShell для Windows. Документ — единственный источник формата: меняется только с увеличением `api`. Исключение — до первого выпуска роутерного пакета: правки без увеличения `api`, с записью в §9.

## 1. Как это устроено

- На роутере работает `rpcd` (штатная часть OpenWRT). Через него страница DpiShell в меню роутера вызывает методы объекта `dpishell`. Windows-приложение вызывает **те же методы тем же путём** — отдельного сервера для приложения нет.
- Транспорт: JSON-RPC 2.0, `POST http://<адрес роутера>/ubus`, `Content-Type: application/json`.
- Роутер принимает запросы только из домашней сети (uhttpd слушает LAN, fw4 закрывает WAN).

## 2. Поиск роутера

1. Адрес по умолчанию — основной шлюз IPv4 активного адаптера (у пользователя сейчас `192.168.1.1`; после сторонняя прошивка OpenWrt обычно `192.168.1.1`). В настройках можно указать свой адрес (IP или имя, без схемы и пути).
2. `GET http://<адрес>/dpishell/status.json`, таймаут 1 с, без входа. Роутер с DpiShell — если `product == "dpishell-router"`. Формат — `06-router-spec.md` §5.2 + поле `"api": 1`.
3. Нет ответа / 404 / другой `product` — «На роутере DpiShell не найден». Приложение работает как раньше, только с ПК.
   - Роутер может стоять не первым: «роутер провайдера → наш роутер → ещё один роутер/Mesh → ПК». Если по шлюзу DpiShell не найден, приложение пробует ещё до 3 частных адресов на пути наружу (первые узлы `tracert -d -h 4`, только `10/8`, `172.16/12`, `192.168/16`), тем же запросом с таймаутом 1 с. Найден не на шлюзе — управление так же, вход по паролю того роутера.
4. `api` у роутера больше, чем знает приложение — «Обновите приложение», разрешено только чтение статуса. Меньше или поля `api` нет — «Обновите пакет на роутере», только чтение статуса.

## 3. Вход

```json
→ {"jsonrpc":"2.0","id":1,"method":"call","params":["00000000000000000000000000000000","session","login",{"username":"root","password":"<пароль>","timeout":600}]}
← {"jsonrpc":"2.0","id":1,"result":[0,{"ubus_rpc_session":"c1ed6c7b…","timeout":600,"expires":600,…}]}
```
- Пароль — пароль администратора роутера (тот же, что для меню). Хранится на ПК через DPAPI (`ProtectedData`, `CurrentUser`), в логи и отчёты не попадает.
- Сессия живёт `timeout` секунд с последнего вызова. Неверная или истёкшая сессия: штатный `uhttpd-mod-ubus` отвечает ошибкой JSON-RPC `{"error":{"code":-32002,"message":"Access denied"}}` без `result`; вызов, на который у сессии нет прав, может вернуть `result[0] == 6`. Оба случая — «нет доступа»: войти заново один раз; снова — «Неверный пароль или сессия», запросить пароль.
- `result[0] == 6` на `login` — неверный пароль.

## 4. Вызов метода

```json
→ {"jsonrpc":"2.0","id":2,"method":"call","params":["<ubus_rpc_session>","dpishell","<метод>",{…аргументы…}]}
← {"jsonrpc":"2.0","id":2,"result":[0,{…ответ…}]}
```
- `result[0]` — код ubus: `0` успех, `2` неверные аргументы, `4` метода/объекта нет (пакет не установлен или старый), `6` нет доступа, `7` таймаут, `5` ответа нет.
- Ошибка уровня DpiShell при коде `0`: `{"error":{"code":"busy","text":"Идёт подбор"}}`. Коды: `busy`, `not_installed` (ядро не загружено), `invalid` (с полем `field`), `conflict` (работает чужой обход), `core_mismatch` (хеш ядра), `failed` (с `text`). У всех кодов `text` — готовая фраза для пользователя.
- `field` при `invalid` — путь к значению в аргументах: `items[3].url`, `items[0].roles.google`, `hours`. Индексы с нуля.
- Таймаут HTTP — 10 с. Долгие операции (подбор, проверка, загрузка ядра) только запускаются и возвращаются сразу; ход — опросом `status`/`select_progress` раз в 1 с.

## 5. Методы

Время — ISO 8601 UTC. Идентификаторы стратегий — как в `strategies.json` / `user-strategies.json`.

### 5.1 Чтение

**`status`** `{}` →
```json
{ "api": 1, "version": "0.1.0", "engine": "zapret1",
  "core": { "version": "v72.13", "installed": true, "hash_ok": true },
  "enabled": true, "mode": "all", "strategy": "alt10", "backups": ["alt9", "alt13"], "needs_tcp_timestamps": true,
  "last_check": { "at": "2026-10-16T21:00:00Z", "source": "timer", "ok": true,
                  "groups": [ { "id": "youtube", "ok": true }, { "id": "discord", "ok": true } ] },
  "fail_streak": 0,
  "schedule": { "enabled": true, "hours": 1, "auto_select": false },
  "jobs": { "select": false, "check": false, "core_install": false, "dns_analyze": false, "site_check": false },
  "warnings": [ { "code": "flow_offload", "text": "Включён flow offloading" } ] }
```
`source`: `manual` | `timer` | `app`. Коды `warnings`: `flow_offload`, `ipv6`, `dns_spoofed`, `conflict`, `core_missing`, `switched_backup` (сработала запасная стратегия, в `text` — какая), `auto_selected` (автоподбор нашёл и включил стратегию, в `text` — какую), `auto_select_failed` (автоподбор ничего не нашёл, оставлена прежняя), `dns_fallback` (защищённый DNS недоступен, временно DNS провайдера).

**`strategies`** `{}` → `{ "catalog_version": 3, "items": [ { "id": "alt10", "title": "general (ALT10)", "source": "catalog|user", "runs": 7, "passed": 6 } ] }` — порядок как в списке выбора (по статистике).

**`select_progress`** `{}` →
```json
{ "running": true, "started_by": "app", "depth": "main", "index": 4, "total": 20, "eta_s": 95,
  "message": "alt3: YouTube",
  "rows": [ { "id": "alt", "title": "general (ALT)", "group_share": 1.0, "target_share": 0.88, "avg_s": 0.74, "error": null } ],
  "finished_at": null, "cancelled": false, "best": null, "applied": false, "backups": [] }
```
`title` в строках `rows` — всегда: название из каталога или описание кандидата глубокого поиска (кандидаты в `strategies` не попадают). `started_by`: `page` | `app` | `auto` («Включить» без стратегии) | `timer` (автоподбор после неудачной проверки). `eta_s` — оценка оставшегося времени, `null`, пока не известна (глубокий поиск сужает перебор по ходу). После завершения — `best`, `applied: true` (подбор сам включил лучшую, 06-router-spec §3.3) и `backups` (до 3 запасных). Остановленный подбор — `cancelled: true`, `applied: false`, прежнее состояние восстановлено.

**`targets_get`** `{}` → `{ "items": [ { "url": "https://example.com/", "important": true } ] }` — только «Свои адреса» роутера.

**`lists_get`** `{ "name": "user-general" | "user-exclude" | "exclude" }` → `{ "lines": ["example.com"], "editable": true }` — `exclude` (стандартные исключения) только для чтения.

**`diag`** `{}` → `{ "conflicts": [ { "kind": "service", "name": "zapret2", "running": true } ], "flow_offload": false, "ipv6_wan": false, "dns": { "spoofed": true, "checked_at": "…" }, "overlay_free_kb": 18000 }`.

**`site_check_result`** `{}` → `{ "running": false, "url": "https://example.com/", "with_bypass": { "ok": false, "detail": "сброс после 16 КБ" }, "without_bypass": { "ok": true, "detail": "" }, "suggest_exclude": true }` — `suggest_exclude`: открывается только без обхода, предложить добавить в исключения (`lists_set user-exclude`).

**`report`** `{}` → `{ "text": "…" }` — то же, что «Сохранить отчёт» на странице.

**`dns_status`** `{}` → `{ "mode": "provider" | "doh", "spoofed": true, "checked_at": "…", "servers": [ { "name": "Google", "doh_ok": true, "ms": 38 }, { "name": "Cloudflare", "doh_ok": true, "ms": 41 } ], "fallback_active": false }` — `job` — последнее DNS-задание: `{ "action": "dns_enable", "running": false, "ok": true, "message": "Готово" }` (установка пакета занимает 10–20 с, поэтому `dns_enable`/`dns_restore` фоновые, как подбор). `fallback_active`: оба DoH пропали, временно работает DNS провайдера (06-router-spec §3.8).

### 5.2 Действия

| Метод | Аргументы | Что делает | Ответ |
|---|---|---|---|
| `enable` | `{}` | включает обход с текущей стратегией | `{}` или `error` |
| `disable` | `{}` | выключает | `{}` |
| `mode_set` | `{ "mode": "all" \| "lists" }` | «Все сайты, кроме исключений» / «По спискам»; перезапуск zapret и полная проверка с контрольной группой (06-router-spec §3.4) | `{ "started": true }` |
| `site_check` | `{ "url": "https://example.com/" }` | «Сайт не открывается с обходом»: проверка с обходом и без; ход — `status.jobs.site_check`, итог — `site_check_result` | `{ "started": true }` |
| `strategy_set` | `{ "id": "alt9" }` | выбор стратегии; при включённом обходе — перезапуск | `{}` |
| `check_now` | `{}` | запускает проверку (результат — в `status.last_check`, `source: app`) | `{ "started": true }` |
| `select_start` | `{ "groups": ["youtube","discord","user"], "mode": "full" \| "quick", "depth": "main" \| "deep" }` | запускает подбор; `deep` — глубокий поиск по 02-spec §4.7 (генерация кандидатов по ролям, ориентир 5–15 мин), `main` — готовые стратегии (~2–3 мин) | `{ "started": true }` |
| `select_cancel` | `{}` | останавливает, возвращает прежнее | `{}` |
| `apply` | `{ "id": "alt9", "backups": ["alt13"] }` | выбрать другую стратегию из итога подбора вместо автоматически включённой | `{}` |
| `schedule_set` | `{ "enabled": true, "hours": 1, "auto_select": false }` (`hours` ∈ 0.5, 1, 3, 6, 12, 24) | таймер проверки; `auto_select` — при неудаче проверки и исчерпанных запасных роутер сам запускает быстрый подбор (06-router-spec §3.5) | `{}` |
| `targets_set` | `{ "items": [ { "url": "…", "important": true } ] }` | свои адреса (до 50) | `{}` |
| `lists_set` | `{ "name": "user-general", "lines": [ … ] }` | свои списки (домены по шаблону, до 5000 строк) | `{}` |
| `strategies_user_set` | `{ "items": [ { "id": "u-…", "title": "…", "roles": { "google": "…" } } ] }` — `id` по шаблону `^u-[a-z0-9-]{1,48}$`, `title` до 80 символов; роли и значения — в той же записи, что `strategies.json` (§5.3) | загрузить найденные на ПК стратегии (§6); заменяет весь прежний набор из приложения | `{}` или `error: invalid` |
| `dns_analyze` | `{}` | анализ DNS (06-router-spec §3.8), результат — в `dns_status` | `{ "started": true }` |
| `dns_enable` | `{}` | включить защищённый DNS для всей сети, прежние настройки сохраняются | `{ "started": true }` |
| `dns_restore` | `{}` | вернуть DNS как было | `{ "started": true }` |
| `conflict_stop` | `{ "name": "zapret2" }` (только имя из `diag.conflicts`) | остановить и отключить чужой обход | `{}` |
| `core_install` | `{}` | загрузить ядро по манифесту | `{ "started": true }` |

Роутер проверяет всё сам: стратегии — по `options.json`, домены — по шаблону, длины — по лимитам. Командной строки и путей от клиента не принимает.

### 5.3 Запись стратегии
- Набор ролей **не фиксирован**: он будет расти (игровые профили, обновляемый ipset — аудит Windows-стороны). Роутер принимает роли, которые знает его каталог (`strategies.json` той версии, что в пакете; `catalog_version` в `strategies`). Сейчас это `quic`, `discord_udp`, `discord_media`, `google`, `general`, `ipset_udp`, `ipset_tcp`. Роль, неизвестная роутеру, — `invalid` с `field` на неё; приложение не отбрасывает роли само, а при таком ответе предлагает обновить пакет на роутере.
- Значения — как в `strategies.json`: `{fake}/<файл>.bin` (набор файлов `fake/` у роутера тот же, 06-router-spec §2.3), `0x…`, `!`. Подстановку `{fake}` роутер разворачивает сам. Файл, которого нет в его `fake/`, — `invalid`.

## 6. Что приложение делает с этим (для Windows-стороны)

- **Настройки → «Роутер»**: адрес (по умолчанию «Автоматически — основной шлюз»), пароль, кнопка «Подключиться», строка состояния («Подключено, DpiShell 0.1.0» / «DpiShell на роутере не найден» / «Неверный пароль»).
- **Главный экран**, если роутер найден и обход на нём включён: блок «Обход делает роутер — стратегия N, проверено в 14:00». Кнопки: Включить/Выключить на роутере, Проверить, Подобрать на роутере, выбор стратегии. **Обход на ПК и обход на роутере одновременно не работают** (решение пользователя 2026-10-17): пакеты, изменённые обходом ПК, роутер изменяет второй раз — стратегии ломаются непредсказуемо, а подбор на ПК находит стратегии, работающие только «в паре» с роутером.
  - Пока `status.enabled == true`, «Включить» на ПК не включает обход на ПК, а предлагает: «Обход уже работает на роутере» и кнопки «Подобрать на роутере» / «Выключить на роутере и включить на этом ПК».
  - Подбор на ПК при `enabled == true` не стартует: «Выключить обход на роутере на время подбора» (`disable`, после подбора — вопрос «Включить на роутере обратно?» и `enable`) или «Подобрать на роутере».
  - Это решение по факту «включён», а не по тому, открываются ли сайты: сломанная стратегия на роутере всё равно обрабатывает пакеты.
  - Обход на ПК уже включён, а роутер сообщает `enabled == true` (включили со страницы роутера или с другого ПК) — приложение выключает обход на ПК и сообщает «Обход перешёл на роутер».
- **Подбор на роутере**: тот же диалог, что для ПК (группы, режим, глубина), таблица из `select_progress`, «Применить на роутере».
- **Стратегия с ПК → на роутер**: найденную глубоким поиском на ПК стратегию можно отправить на роутер (`strategies_user_set` + `strategy_set`). Путь ПК → провайдер идёт через роутер, поэтому стратегия, найденная на ПК при выключенном обходе на роутере, обычно подходит и роутеру; после отправки — `check_now`.
- **Свои адреса и списки роутера** — отдельная вкладка «На роутере» в тех же экранах, с ПК не синхронизируются автоматически (кнопка «Скопировать с ПК»).
- **DNS роутера**: в разделе DNS — «Для всей сети (роутер)»: `dns_status`, «Проверить», «Включить защищённый DNS» с теми же последствиями, что на странице роутера, «Вернуть как было».
- **Диагностика**: раздел «Роутер» — `diag`, кнопки «Остановить» у конфликтов, «Сохранить отчёт роутера».
- **Временные метки TCP** (`needs_tcp_timestamps: true` — включённая на роутере стратегия работает только у устройств с метками): приложение включает метки на этом ПК само, как перед своим подбором (09-features-spec, решение 8), и пишет одной строкой «Включены временные метки TCP — нужны стратегии роутера». Выключать обратно при уходе из сети не нужно — метки ничему не мешают.
- Сеть сменилась (ноутбук ушёл из дома) — роутер не найден, блок пропадает, приложение работает как обычно.

## 7. Тестирование без роутера

Роутерной стороны пока нет. Для тестов Windows-стороны — фейковый сервер в памяти (`HttpListener` или `TestServer`), который отвечает по этому документу: примеры ответов — разделы 3–5 дословно. Случаи для тестов: роутер не найден; `status.json` без `api`; неверный пароль; истёкшая сессия (JSON-RPC `-32002` и `result[0] == 6` → повторный вход → успех); метод отсутствует (`4`); `busy`; `invalid` с `field`; подбор от `running: true` до `best` + `applied: true`; остановленный подбор (`cancelled`); подбор, запущенный не приложением (`started_by: page`).

## 8. Вопросы Windows-стороны (2026-10-16) — отвечены

Ответы внесены в разделы выше; кратко — в конце каждого пункта.

1. **`status.json` без поля `api`** (случай из §7). §2.4 описывает только «больше» и «меньше». Сейчас приложение считает отсутствие `api` старым пакетом: «Обновите пакет на роутере», только чтение статуса. Подтвердить или указать иное.
   - **Ответ:** подтверждаю — как старый пакет, только чтение (§2.4).
2. **«Нет доступа» при истёкшей сессии.** По договору — `result[0] == 6`. Штатный `uhttpd-mod-ubus` при неверной/истёкшей сессии отвечает ошибкой JSON-RPC `{"error":{"code":-32002,"message":"Access denied"}}`, без `result`. Приложение сейчас принимает оба варианта как код 6 (повторный вход один раз). Какой из них роутер возвращает на самом деле — зафиксировать в §3–4.
   - **Ответ:** штатный роутер отвечает JSON-RPC `-32002`; `result[0] == 6` — при нехватке прав у сессии и на `login` с неверным паролем. Принимать оба, как сейчас (§3).
3. **`strategies_user_set`, формат стратегии.**
   - `id`: приложение шлёт `u-` + id на ПК, например `u-found-261016-2213-2`. Допустимые символы и длина?
   - Значения ролей на ПК содержат подстановку `{fake}/<файл>.bin` (например `--dpi-desync-fake-tls={fake}/tls_clienthello_www_google_com.bin`) и `!` (встроенный фейк). Принимает ли роутер эту же запись и тот же набор файлов `fake/`? Если нет — в каком виде отправлять.
   - Набор ролей на ПК: `quic`, `discord_udp`, `discord_media`, `google`, `general`, `ipset_udp`, `ipset_tcp`. Совпадает ли с ролями роутера (§4.2 `06-router-spec.md`)? Роли, которых у роутера нет, — отбрасывать на ПК или роутер вернёт `invalid`?
   - **Ответ:** id — `^u-[a-z0-9-]{1,48}$` (ваш формат подходит); `{fake}/…` и `!` — та же запись, тот же набор файлов; роли — из каталога роутера (набор будет расти), неизвестная — `invalid`, на ПК не отбрасывать (§5.2, §5.3).
4. **`error.field` при `invalid`** — что в нём: имя аргумента (`items`), путь (`items[3].url`)? Нужно, чтобы показать пользователю, какая строка не понравилась роутеру.
   - **Ответ:** путь к значению, `items[3].url` (§4).
5. **`select_start` с `depth: "deep"`** — это глубокий поиск по `02-spec.md` §4.7 (генерация кандидатов) или «основные + расширенный каталог»? Сколько длится — чтобы показать оценку времени.
   - **Ответ:** глубокий поиск по 02-spec §4.7, 5–15 мин; ход — `eta_s` в `select_progress` (§5.1).
6. **Подбор, запущенный с другого устройства.** Если `jobs.select == true`, а приложение подбор не запускало, — показывать ход (`select_progress`) и разрешать `select_cancel`? Приложение сейчас так и делает.
   - **Ответ:** да, показывать и разрешать отмену; кто запустил — `started_by` (§5.1).
7. **Автоподбор на роутере по расписанию** (решение пользователя 2026-10-16: на ПК автопроверки нет, она нужна только на роутере). Нужно поле для `schedule_set`/`status.schedule`, например `"auto_select": true`: если проверка не прошла и запасные не помогли — роутер сам запускает быстрый подбор и применяет лучшую без `apply` от клиента (и без `restore_at`). Итог — в `status.warnings` (код, например, `auto_selected`, в `text` — какая стратегия). Пока поля нет, приложение показывает только «Проверять по расписанию» + «при неудаче — запасная».
   - **Ответ:** да: `auto_select` в `schedule`/`schedule_set`, по умолчанию `false`. Автоподбор — быстрый, готовые стратегии (`depth: main`), не чаще раза в 6 ч, `started_by: timer`, применяет сам; итог — `auto_selected` или `auto_select_failed` в `warnings`. Ход виден в `select_progress`, отменить можно (§5.1, §5.2).
8. **Названия в `select_progress.rows`** (2026-10-17, отвечен). Таблица подбора берёт названия из `strategies`. Глубокий поиск (`depth: deep`) проверяет кандидатов, которых в `strategies` ещё нет, — у такой строки только `id`, и приложение показывает его как есть. Добавить `title` в строки `rows` (или кандидаты сразу попадают в `strategies`)?
   - **Ответ:** `title` в каждой строке `rows`: у готовых — название из каталога, у кандидатов — короткое описание приёма («fake + multisplit, ts — YouTube»). Кандидаты в `strategies` не попадают — только найденные в финале глубокого поиска (`source: user`) (§5.1).

# DNS: подмена ответов провайдером и что с ней делать

Почему в DpiShell проверка сайтов не доверяет системному DNS, зачем нужны кнопки «DNS этого компьютера» и «DNS для всей сети» и какие у смены DNS последствия. Как это реализовано — [../dev/architecture.md](../dev/architecture.md) (разделы «DNS»).

## Что происходит

На части провайдеров подменяются ответы обычного DNS (UDP 53) — в том числе к сторонним серверам вроде `8.8.8.8`: заблокированное имя получает «имени нет» (NXDOMAIN) или адрес-заглушку. Браузеры при этом ходят в DoH сами, поэтому сайт в браузере открывается, а программы, которые пользуются системным DNS (Discord, игры, проверки вроде `curl`/Flowseal), получают неверный адрес. Следствия для оболочки обхода:

1. **Проверка стратегий не должна зависеть от DNS системы.** Иначе «не открылось» означает подмену имени, а не неработающую стратегию. Поэтому проба резолвит цели сама через DoH (`dns.google`, `cloudflare-dns.com` — по IP) и подключается к полученному адресу.
2. **Отдельно сравнивается системный DNS с DoH.** Расхождение (множества адресов не пересекаются) — предупреждение «DNS провайдера подменяет адреса: приложения вне браузера не будут работать» и предложение переключить DNS в один клик.
3. **DoH чинит только подмену имени.** Если провайдер блокирует сам IP, DoH честно выдаст тот же недоступный адрес — это другая поломка (см. hosts в [flowseal-features.md](flowseal-features.md) §4).

## Что проверяется при анализе DNS

Кандидаты: текущий DNS системы, DNS роутера/провайдера (из DHCP), Google (8.8.8.8), Cloudflare (1.1.1.1), Quad9 (9.9.9.9), AdGuard (94.140.14.14, с фильтром рекламы — помечен отдельно). Яндекс DNS (77.88.8.8) в список рекомендуемых не входит: российские резолверы обязаны применять реестр блокировок (вариант есть, с пометкой).

Для каждого — по контрольным доменам (YouTube, Discord, свои адреса пользователя + нейтральные `example.com`, `wikipedia.org` как эталон «всё работает»):
1. **Обычный DNS (UDP 53)**: ответ совпадает с эталоном (консенсус двух DoH-серверов по пересечению адресов/подсетей — CDN отдают разные IP, поэтому сравниваем по /16 и владельцу), подмена (NXDOMAIN, адрес-заглушка, `0.0.0.0`/`127.0.0.1`), таймаут.
2. **DoH (443)**: доступен ли вообще (сам `dns.google` бывает под DPI — тогда с обходом и без), время ответа (медиана из 5).
3. **Внутренние имена**: резолвит ли текущий DNS что-то, чего нет в публичном DNS — суффиксы поиска DNS адаптера, домен Active Directory (`USERDNSDOMAIN`), имена локальной сети (`*.local`, `*.lan`, `*.home.arpa`, имя роутера). Такие имена — признак, что смена DNS их сломает.

## Последствия смены DNS (показываются до применения)

| Последствие | Когда | Что делать |
|---|---|---|
| Перестанут открываться внутренние адреса (корпоративная сеть, домен AD) | найдены внутренние имена или ПК в домене | предупреждение крупно; правила NRPT (`Add-DnsClientNrptRule`) оставляют внутренние суффиксы на прежнем DNS |
| Не находятся устройства домашней сети по имени (роутер, принтер, NAS) | роутер отвечает на локальные имена | NRPT для `.lan`/`.local`/`.home.arpa` и имени роутера; на роутере — не страдают: их отвечает dnsmasq |
| Корпоративный VPN | VPN-адаптер со своим DNS | менять DNS только на физических адаптерах; VPN и виртуальные (Hyper-V, WireGuard, TAP, Tailscale…) не трогать |
| Пропадёт фильтрация провайдера/роутера (родительский контроль, блок рекламы) | DNS роутера отличается от провайдера | сообщение «фильтрация роутера перестанет действовать» |
| Сайты чуть медленнее (CDN выбирает сервер по местоположению DNS) | всегда | строка в пояснении, замер скорости |
| Нет интернета через гостиничный/общественный Wi-Fi до страницы входа | ноутбук | «Вернуть как было» на время входа |
| DoH-сервер недоступен — DNS не работает целиком | возврат к обычному тексту выключен | два сервера разных компаний; проверка доступности до применения; проверка после переключения с автоматическим откатом; на роутере — временный возврат к DNS провайдера по таймеру |
| Устройства с жёстко прописанным DNS (часть ТВ/приставок) | бывает | обходят роутер; перехват порта 53 — не в первой версии |

## Почему по умолчанию без возврата к обычному DNS

Если DoH не отвечает и Windows тихо возвращается к обычному DNS, провайдер снова подменяет ответы незаметно для пользователя. Поэтому режим по умолчанию — «только защищённый», а безопасность первого включения обеспечивает **проверка после переключения** (помощник сбрасывает кэш и несколько раз проверяет, что имена разрешаются; нет — сам возвращает прежние настройки). Отдельная галочка «если защищённый не отвечает — обычный DNS» — для сетей, где DoH-сервер то блокируют, то нет.

## Что проверено по открытым данным

- Windows 11 хранит включение DoH на адаптере в `HKLM\SYSTEM\CurrentControlSet\Services\Dnscache\InterfaceSpecificParameters\{GUID}\DohInterfaceSettings\Doh|Doh6\<адрес>` (`DohFlags`, `DohTemplate`); документирована только команда `netsh dnsclient add encryption`. У `DohFlags` документации нет — значение может поменяться в обновлении Windows; бит «возврат к обычному тексту» проверяется по тому, что показывает «Параметры». Windows 10 встроенного DoH не имеет — там только обычный DNS с честной подписью «без шифрования».
- Встроенные шаблоны Google/Cloudflare/Quad9 уже есть в `Dnscache\Parameters\DohWellKnownServers`; для своих адресов шаблон регистрируется `netsh dnsclient add encryption … autoupgrade=no`.
- DoH Яндекса — `https://common.dot.dns.yandex.net/dns-query` (проверено запросом RFC 8484 по обоим адресам; отвечает только по HTTP/2; имя `common.doh…` не существует).
- На OpenWrt защищённый DNS для всей сети даёт штатный пакет `https-dns-proxy`: сразу после установки он сам переключает dnsmasq на свои экземпляры (`noresolv=1`, `server=127.0.0.1#5053/5054`) и объявляет канарейку `use-application-dns.net` (выключает DoH в Firefox). После `apk del` dnsmasq сам не перезапускается — DNS роутера пропадает, перезапуск нужен явно. С одним адресом `bootstrap` https-dns-proxy падает в цикле — адрес передаётся дважды.

# Аудит: DpiShell на роутере (OpenWRT)

Дата: 2026-10-16. Только чтение источников. Подробные заметки со ссылками — `docs/research/router-*.md`.

## Итог

1. **Движок — тот же nfqws из zapret v1 (bol-van v72.13)**, что и winws на Windows: один исходник, все параметры нашего каталога есть. Бинарник берём из релиза bol-van по закреплённому хешу под архитектуру роутера.
2. **Каталог стратегий и цели — общие с Windows.** Меняется только обвязка: `--wf-tcp/--wf-udp` → порты в config zapret.
3. **Готового решения под наше ТЗ нет.** remittor/luci-app-zapret — без автоподбора и с широкими правами; Zapret Manager (StressOzz) — без лицензии, исполняет скачанный код без проверки. Берём идеи, делаем своё.
4. **Своё = пакет `dpishell` (LuCI-страница на JS + rpcd на ucode + подбор на curl)**, официальные скрипты zapret для правил nftables. Без своих бинарников: один пакет на все архитектуры.
5. **Подбор — с самого роутера**: трафик роутера идёт через те же правила nfqws, что и трафик клиентов. curl 8.22 в OpenWRT 25.12 умеет TLS 1.3 и чтение тела; HTTP/3 не умеет — QUIC на роутере «не проверялся».
6. **Веб-интерфейс** — в меню роутера (LuCI), вход по паролю роутера; короткий адрес `http://192.168.1.1/dpi`.
7. **Windows-версия видит роутер** по файлу `http://<шлюз>/dpishell/status.json` и не включает свой обход.
8. Требования к роутеру: OpenWRT 25.12+ (apk) с fw4/nftables и `kmod-nft-queue` в фиде прошивки под её ядро; ресурсы — любые современные (nfqws видит только первые пакеты соединения).

## 2. zapret на OpenWRT

**Установка по документации bol-van v72.13** ([quick_start.md](https://github.com/bol-van/zapret/blob/v72.13/docs/quick_start.md)):
- Релиз `zapret-v72.13-openwrt-embedded.tar.gz` (sha256 `b2a9f454…c2e6`, совпадает с digest GitHub): бинарники `binaries/linux-{arm,arm64,mips,mipsel,…}/nfqws`, скрипты, фейки.
- `install_bin.sh` выбирает архитектуру; `install_easy.sh` ставит в `/opt/zapret`, понимает и `opkg`, и `apk` (OpenWRT 25.12 перешёл на apk).
- Пакеты: `curl nftables kmod-nft-nat kmod-nft-offload kmod-nft-queue`. В неофициальных прошивках `kmod-nft-queue` и `curl` могут отсутствовать в образе — ставятся из фида прошивки (модули — строго под её ядро).
- Служба — procd (`/etc/init.d/zapret`). Конфиг `/opt/zapret/config`: `NFQWS_OPT` (профили через `--new`), `NFQWS_PORTS_TCP/UDP`, `MODE_FILTER`, `FLOWOFFLOAD`, `DISABLE_IPV6`. Своя таблица nft `inet zapret`, правила fw4 не трогаются.
- Официального пакета zapret в репозиториях OpenWRT нет.

**Как ловится трафик** ([nft.sh](https://github.com/bol-van/zapret/blob/v72.13/common/nft.sh)):
- Правило `oifname @wanif tcp dport {…} ct original packets 1-9 queue num 200 bypass` в цепочке postrouting после NAT. nfqws видит только первые пакеты соединения, поэтому нагрузка на CPU мала. На слабых MIPS без этого ограничения nfqws подвешивал роутер ([#56](https://github.com/bol-van/zapret/issues/56)).
- Hook postrouting видит **и транзитный трафик клиентов, и трафик самого роутера**; фильтра по пользователю у правил nfqws нет. Поэтому curl на роутере проходит через ту же стратегию, что и устройства в сети. На этом держится подбор с роутера.
- Отличия «с роутера» и «через роутер»: `badsum` на роутерах MediaTek через роутер не проходит; `datanoack` ломает NAT только с iptables. Наш каталог использует `ts`, `badseq`, `md5sig` — не затронуты.
- **Системный flow offloading несовместим с nfqws**: соединение, попавшее в flowtable, nfqws больше не видит. zapret умеет вести разгрузку сам (`FLOWOFFLOAD=software|hardware`) с исключением для пакетов nfqws — это и делает кнопка «Передать zapret». Аппаратная разгрузка NAT в отдельных прошивках (PPE и т. п.) — проверять на месте.
- IPv6 в zapret по умолчанию выключен. Если провайдер даёт IPv6, YouTube пойдёт мимо обхода — нужно включать IPv6 в zapret или предупреждать.

**blockcheck.sh на роутере** — умеет работать без вопросов (`BATCH=1 DOMAINS=… SCANLEVEL=quick`), вывод можно разобрать. Но HTTPS по умолчанию проверяет запросом HEAD, тело не читает; нет групп целей, нет порога 20 КБ, нет стратегий из нескольких профилей (QUIC + Discord + TCP разом). **Как основа подбора не годится**; полезен как источник порядка перебора (tier 2 нашего каталога) и проверки подмены DNS.

**curl в OpenWRT 25.12** ([Makefile](https://github.com/openwrt/packages/blob/openwrt-25.12/net/curl/Makefile)): версия 8.22, TLS через mbedtls 3.6 — TLS 1.3 есть. HTTP/3 выключен при сборке (нужна OpenSSL-сборка) → QUIC-цели на роутере «не проверялись», как и на Windows без HTTP/3. Отпечаток TLS у curl не такой, как у браузера, — стратегия может отличаться в редких случаях; проверка с ПК закрывает это (раздел 5).

## 3. Перенос каталога winws → nfqws

- `nfqws.c` и `winws` — один исходник; Windows-только опции: `--wf-*`, `--ssid-filter`, `--nlm-filter`. **Все десинк-параметры `data/strategies.json` (около 30) есть в nfqws v72.13** — таблица в `research/router-nfqws.md` §5.
- В сборщике командной строки меняется:
  - `--wf-tcp=80,443,2053,2083,2087,2096,8443` → `NFQWS_PORTS_TCP` в config;
  - `--wf-udp=443,19294-19344,50000-50100` → `NFQWS_PORTS_UDP`;
  - `--qnum`, `--user`, `--dpi-desync-fwmark` добавляет init-скрипт zapret;
  - профили ролей (`--filter-tcp/udp … --hostlist … --new`) идут в `NFQWS_OPT` без изменений, `MODE_FILTER=none`.
- `{fake}/*.bin`: в zapret есть 3 из 8 используемых; остальные 5 (Flowseal: `ACTIVE_DISCORD_UDP`, `max_ru`, `4pda_to`, `stun2`, `sochi_park`) везём в пакете — они уже проверены (`03-vetting.md`).
- Встроенный фейк `--dpi-desync-fake-tls=!`: в каталоге было `^!` из .bat (nfqws и winws искали бы файл «^!»), исправлено в a1aad39.

Вывод: подбора с нашим критерием (полное тело > 20 КБ, группы, «важные» свои адреса) в одном пакете с узкими правами и закреплёнными хешами нет ни у кого. Ближе всего по логике — b4 и nfqws2-ui; их схемы берём как образец.

Про zapret2: все активные роутерные интерфейсы переходят на nfqws2 (Lua-стратегии), но ветка v1 жива (коммит 2026-10-04, репозиторий не в архиве). Каталог под nfqws2 не переносится; остаёмся на v1 вместе с Windows, адаптер движка (02-spec §4.2) оставляет дорогу к v2.

## 5. Веб-интерфейс и подбор на роутере

**LuCI-приложение против отдельного сервиса:**

| | LuCI (JS + rpcd на ucode) | Отдельный сервис (Go / shell + uhttpd) |
|---|---|---|
| Где | меню роутера «Службы → DpiShell» | свой порт |
| Вход | пароль роутера, сессии LuCI | писать самим |
| Права | ACL rpcd: только наши ubus-методы | сервис от root, проверка прав — сами |
| Размер | десятки КБ, без бинарников | Go-бинарник 2–5 МБ под каждую архитектуру |
| Телефон | тема Bootstrap адаптивная; наша страница — простые карточки | любая вёрстка |

**Берём LuCI**: вход, HTTPS при желании и права уже есть. ucode — родной язык rpcd в OpenWRT 23+: JSON и файлы без внешних зависимостей. Короткий адрес `http://192.168.1.1/dpi` — статическая страница с переадресацией в LuCI.

**Подбор с роутера:**
- curl с роутера проходит через те же правила, что и клиенты (раздел 2), поэтому проверка честная.
- Чтение тела: `curl -o /dev/null -w '%{http_code} %{size_download} %{redirect_url}'`; обрыв даёт код выхода 18/56. Тот же критерий, что `02-spec` §4.3.
- Во время подбора обход для всей сети переключается на проверяемую стратегию: тестируем ровно ту обвязку, что потом применится. Клиенты на ~3 минуты могут потерять обход — так же, как на Windows останавливается служба.
- Изоляция подбора от клиентов (отдельный nfqws на своей очереди, curl с диапазона исходных портов, `tcp sport` в nft) реалистична и проще, чем на WinDivert. Но пакет, отпущенный тестовой очередью, пойдёт дальше в боевую цепочку zapret — нужна метка-исключение. **Не проверено** → эксперимент, не v1.

## 6. Связь с Windows-версией

- **Каталог и цели — одни файлы** (`data/strategies.json`, `data/targets.json`). В каталоге поле `engine: "winws"` → `"zapret1"` (общий синтаксис winws/nfqws). Список разрешённых параметров переезжает из `Strategies.cs` в `data/options.json`, чтобы роутер проверял каталог тем же списком.
- **Windows видит роутер**: роутер публикует `http://<шлюз>/dpishell/status.json` (без секретов: версия, включено, стратегия, время последней проверки). Windows при запуске и смене сети читает его с таймаутом 1 с. Если обход на роутере включён — статус «Обход делает роутер», кнопка «Включить» с предупреждением: двойная обработка ломает соединения.
- Проверка «без обхода» на Windows (02-spec §4.4) в домашней сети покажет «блокировок нет» — это и есть подтверждение, что роутер работает. «Проверить сейчас» на ПК проверяет путь клиента — закрывает расхождение отпечатков curl и браузера.

## 7. Если OpenWRT на роутере нет

- **Мини-плата как шлюз** (NanoPi R3S, GL.iNet MT3000/MT6000 — OpenWRT из коробки): основной роутер работает как точка доступа или за платой. Наш пакет ставится без изменений.
- **Keenetic + Entware**: nfqws-keenetic + веб; страницу в меню роутера не встроить — только отдельный порт.
- **ASUS Merlin + Entware**: zapret вручную, готового интерфейса нет.
- **Готовое b4 вместо своего**: движок не zapret — каталог и проверка из `03-vetting` не переносятся.

## 8. Подводные камни

| Что | Чем грозит | Что делаем |
|---|---|---|
| Неофициальная прошивка с частыми релизами | регрессии; модули ядра в фиде не совпадают с ядром образа | перед установкой сверять `kmod-nft-queue` с `uname -r` (офлайн-установщик проверяет сам) |
| Чужой zapret рядом (пакет или менеджер) | два nfqws на одних очередях, затирание `/opt/zapret` | диагностика ищет `zapret`, `zapret2`, `youtubeUnblock`, `b4`, менеджеры zapret; включение и подбор блокируются |
| Flow offload / аппаратная разгрузка | обход не срабатывает на части соединений | предупреждение и «Передать zapret» |
| Быстрый тариф, NAT без разгрузки | упор в CPU роутера | nfqws видит только первые пакеты; разгрузку ведёт zapret с исключением |
| IPv6 от провайдера | обход идёт мимо по v6 | при глобальном адресе на wan6 — предупреждение и «Включить обход по IPv6» |
| Подмена DNS провайдером | стратегия «не работает» на правильном IP | проверки резолвят через DoH; DNS для всей сети — по кнопке (06 §3.8) |
| Обновление прошивки затирает пакеты | обход пропал | пакет из фида переустанавливается; конфиг в `/etc/config/dpishell` сохраняется sysupgrade |
